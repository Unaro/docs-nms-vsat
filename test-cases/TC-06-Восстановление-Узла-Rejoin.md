# TC-06: Восстановление и возврат ранее упавшего узла в кластер (Rejoin)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-06`
- **MMD-диаграмма**: [`mmd/ВосстановлениеПослеПаденияМастер.mmd`](../mmd/ВосстановлениеПослеПаденияМастер.mmd)
- **Цель**: Проверить процедуру возврата восстановившегося узла (`node1`) в действующий кластер, где роль Master исполняет `node2`.
  1. Убедиться в отсутствии паразитного обратного переключения (failback) благодаря параметру `resource-stickiness=100`.
  2. Проверить работу Блока 4 `cluster-boot-analyzer.sh` (v3.0): валидация статуса слота репликации `wal_status` и возможность автоматического выполнения `pg_basebackup` при удалении нужных сегментов WAL на мастере.
  3. Проверить синхронизацию часов Chrony по Ring 0 (Блок 5).
  4. Проверить автоматическое подключение возвратившегося узла исключительно в роли Standby с потоковой репликацией.
- **Объекты проверки**:
  - Предстартовая валидация `cluster-boot-analyzer` (v3.0) на возвращаемом узле.
  - Авто-переинициализация реплики (`pg_basebackup`) при утере WAL или расхождении таймлайнов.
  - Повторное вхождение (Rejoin) в Corosync knet (с Realtime-приоритетом `SCHED_RR`).
  - Сохранение роли Master за `node2` (свойство `resource-stickiness=100`).
  - Опрос сокетов `db-role-check` (:9200) и сохранение маршрутизации HAProxy.

---

## 2. Предусловия
1. Кластер работает в деградированном режиме: `node2` является Master, на нём активны VIP и `app-stack` (состояние после завершения `TC-04`).
2. `node1` был выключен/устранён и готов к включению.
3. На `node2` в процессе работы были записаны новые транзакции.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Включение и загрузка узла node1
**Действие на `node1`:**
Включить питание / загрузить ОС.

### Шаг 2. Контроль предстартовых проверок cluster-boot-analyzer (v3.0)
**Команда на `node1`:**
```bash
journalctl -u cluster-boot-analyzer.service -f --no-tail
```
**Ожидаемый результат:**
1. Проверка ФС (RW-тест, свободное место, `PG_VERSION`) завершена успешно.
2. Проверка смещения часов Chrony: расхождение не превышает `MAX_CLOCK_SKEW_SEC` (1.0 сек).
3. **Блок 4 (WAL-совместимость)**:
   - Скрипт опрашивает соседа `http://10.0.0.2:9200` и получает `HTTP 200 OK Master`.
   - Опрашивает статус слота репликации `slot_node1` на мастере.
   - Выполняет `pg_rewind --dry-run`.
   - Если статус слота `lost` или `pg_rewind` невозможен:
     в логе фиксируется:
     `cluster-precheck: ВНИМАНИЕ: Нужные сегменты WAL на Master удалены... Запускаю автоматический pg_basebackup...`
     Каталог `$PGDATA` очищается и клонируется актуальный снапшот с `node2`.

### Шаг 3. Контроль Rejoin в Corosync
**Команда на обоих узлах:**
```bash
corosync-quorumtool -s
```
**Ожидаемый результат:**
- `Nodes: 2`, `Quorum: 2`, `Quorate: Yes`.
- Оба линка (Ring 0 и Ring 1) находятся в состоянии `connected`.
- Процесс `corosync` работает с приоритетом `SCHED_RR 99` и `OOMScoreAdjust=-1000`.

### Шаг 4. Проверка отсутствия паразитного Failback (Stickiness Check)
**Команда на `node2`:**
```bash
pcs status
```
**Ожидаемый результат:**
- **Критически важно**: `node2` остался `Promoted` (Master)!
- `vip` и группа `app-stack` продолжают работать на `node2` без разрыва сессий.
- Никакого перемещения ресурсов обратно на `node1` НЕ произошло, так как значение `resource-stickiness=100` превышает выгоду локации по умолчанию.

### Шаг 5. Контроль подключения СУБД на node1 в роли Standby
**Команда на `node1`:**
```bash
journalctl -u pacemaker | grep pgsql
```
**Ожидаемый результат:**
1. Pacemaker `pgsqlms` переводит локальную СУБД в роль Standby.
2. Создаётся файл `standby.signal`.
3. PostgreSQL на `node1` запускается в режиме реплики.
4. На `node2` в `pg_stat_replication` появляется запись об успешном подключении реплики `10.0.0.1` со статусом `streaming`.

### Шаг 6. Проверка сокета проверки роли на node1
**Команда на `node1`:**
```bash
curl -i http://127.0.0.1:9200/
```
**Ожидаемый результат:**
```http
HTTP/1.1 503 Service Unavailable
Content-Type: text/plain
Content-Length: 5

Slave
```

### Шаг 7. Итоговый статус кластера
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- Кластер полностью здоров (`Full HA mode`).
- `Promoted: node2`, `Unpromoted: node1`.
- `app-stack`: Started `node2`.
- Ошибок в кластере нет.

---

## 4. Критерии успешности (Pass/Fail)
- **PASS**: `node1` успешно воссоединился с кластером; при утере WAL реплика была автоматически пересоздана через `pg_basebackup`; СУБД на `node1` встала в режим Standby; репликация восстановилась; автоматического переключения мастера на `node1` (failback) НЕ произошло; обслуживание клиентов на `node2` не прерывалось.
- **FAIL**: Возникновение Split-Brain (два мастера), падение `node2` при подключении `node1`, или зависание репликации при нехватке WAL.
