# TC-06: Восстановление и возврат ранее упавшего узла в кластер (Rejoin)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-06`
- **MMD-диаграмма**: [`mmd/ВосстановлениеПослеПаденияМастер.mmd`](../mmd/ВосстановлениеПослеПаденияМастер.mmd)
- **Цель**: Проверить процедуру возврата восстановившегося узла (`node1`) в действующий кластер, где роль Master исполняет `node2`. Убедиться в отсутствии паразитного обратного переключения (failback) благодаря параметру `resource-stickiness=100`, а также в автоматическом подключении возвратившегося узла исключительно в роли Standby с синхронизацией WAL.
- **Объекты проверки**:
  - Предстартовая валидация `cluster-boot-analyzer` на возвращаемом узле.
  - Повторное вхождение (Rejoin) в Corosync knet.
  - Сохранение роли Master за `node2` (свойство `resource-stickiness=100`).
  - Согласование таймлайнов/LSN и запуск PostgreSQL на `node1` как Standby.
  - Опрос сокетов `db-role-check` (:9200) и сохранение маршрутизации HAProxy.

---

## 2. Предусловия
1. Кластер работает в деградированном режиме: `node2` является Master, на нём активны VIP и `app-stack` (состояние после завершения `TC-04`).
2. `node1` был выключен/устранён и готов к включению.
3. На `node2` в процессе работы были записаны новые транзакции.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Включение и загрузка узла node1
**Действие на `node1`:**
Включить питание / загрузить ОС.

### Шаг 2. Контроль прохождения предстартовых тестов на node1
**Команда на `node1`:**
```bash
systemctl status cluster-boot-analyzer.service
```
**Ожидаемый результат:**
- Сервис завершился с кодом `status=0/SUCCESS`.
- Запись маркера `MODE=CRASH_RECOVERY` в `/run/cluster_boot_mode`.
- Диски валидированы, разблокирован запуск `corosync` и `pacemaker`.

### Шаг 3. Контроль Rejoin в Corosync
**Команда на обоих узлах:**
```bash
corosync-quorumtool -s
```
**Ожидаемый результат:**
- `Nodes: 2`, `Quorum: 2`, `Quorate: Yes`.
- Оба линка (Ring 0 и Ring 1) находятся в состоянии `connected`.

### Шаг 4. Проверка отсутствия паразитного Failback (Stickiness Check)
**Команда на `node2`:**
```bash
pcs status
```
**Ожидаемый результат:**
- **Критически важно**: `node2` остался `Promoted` (Master)!
- `vip` и группа `app-stack` продолжают работать на `node2` без разрыва сессий.
- Никакого перемещения ресурсов обратно на `node1` НЕ произошло, так как значение `resource-stickiness=100` превышает выгоду локации по умолчанию.

### Шаг 5. Контроль подключения СУБД на node1 в роли Standby
**Команда на `node1`:**
```bash
journalctl -u pacemaker | grep pgsql
```
**Ожидаемый результат:**
1. Pacemaker `pgsqlms` определяет, что в кластере уже есть подтверждённый Master (`node2`).
2. При наличии расхождений в истории WAL агент выполняет `pg_rewind` от `node2`.
3. Создаётся файл `standby.signal`.
4. PostgreSQL на `node1` запускается в режиме реплики (Standby).
5. На `node2` в `pg_stat_replication` появляется запись об успешном подключении реплики `10.0.0.1` со статусом `streaming`.

### Шаг 6. Проверка сокета проверки роли на node1
**Команда на `node1`:**
```bash
curl -i http://127.0.0.1:9200/
```
**Ожидаемый результат:**
```http
HTTP/1.1 503 Service Unavailable
Content-Type: text/plain
Content-Length: 5

Slave
```

### Шаг 7. Итоговый статус кластера
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- Кластер полностью здоров (`Full HA mode`).
- `Promoted: node2`, `Unpromoted: node1`.
- `app-stack`: Started `node2`.
- Ошибок в кластере нет.

---

## 4. Критерии успешности (Pass/Fail)
- **PASS**: `node1` успешно воссоединился с кластером; СУБД на `node1` автоматически встала в режим Standby; репликация восстановилась; автоматического переключения мастера на `node1` (failback) НЕ произошло; обслуживание клиентов на `node2` не прерывалось.
- **FAIL**: Возникновение Split-Brain (два мастера), падение `node2` при подключении `node1`, или несанкционированный отбор роли Master возвратившимся узлом.
