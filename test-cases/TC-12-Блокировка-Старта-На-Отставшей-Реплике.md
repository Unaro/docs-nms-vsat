# TC-12: Блокировка старта на отставшей реплике (Предохранитель №4)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-12`
- **MMD-диаграмма**: [`mmd/ВосстановлениеПослеПаденияМастерРезерв.mmd`](../mmd/ВосстановлениеПослеПаденияМастерРезерв.mmd)
- **Цель**: Проверить работу предохранителя №4 сторожа деградации: при аварийном старте в одиночку узла, который до аварии являлся репликой (`Slave`), его автоматический промоут в `Master` категорически блокируется, чтобы предотвратить запуск сервисов на устаревшей копии данных и потерю транзакций (RPO > 0).
- **Объекты проверки**:
  - Предохранитель №4 в `/usr/local/sbin/cluster-degraded-unblock.sh`.
  - Анализ статуса базы данных в `pg_controldata` (`in archive recovery`).
  - Запрет выполнения `pcs quorum unblock` для реплики.
  - Сохранение кластера в заблокированном безопасном состоянии.

---

## 2. Предусловия
1. Кластер находился в штатном состоянии: `node1` — Master, `node2` — Slave.
2. Сервер `node1` выключен (сымитирован отказ основного узла).
3. Сервер `node2` перезагружен.
4. Шлюз `192.168.1.1` доступен с `node2`.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Контроль статуса СУБД на node2 при старте
**Команда на `node2`:**
```bash
/usr/lib/postgresql/16/bin/pg_controldata /var/lib/postgresql/16/main | grep "Database cluster state"
cat /run/cluster_boot_mode
```
**Ожидаемый результат:**
- Статус базы: `Database cluster state: in archive recovery`.
- В `/run/cluster_boot_mode`:
  ```text
  MODE=CRASH_RECOVERY
  DB_RAW_STATE=in archive recovery
  ```

---

### Шаг 2. Контроль срабатывания предохранителя №4
**Команда на `node2` после истечения таймаута:**
```bash
journalctl -t cluster-watchdog -n 20 --no-pager
```
**Ожидаемый результат:**
- Сторож фиксирует:
  ```text
  cluster-watchdog: СТОП: Узел до выключения/аварии не был Master (MODE=CRASH_RECOVERY, DB=in archive recovery).
  ```
- Команда `pcs quorum unblock` **не выполняется**.
- Код возврата сторожа — `1`.

---

### Шаг 3. Контроль статуса ресурсов
**Команда на `node2`:**
```bash
pcs status
```
**Ожидаемый результат:**
- Кворум заблокирован (`Quorate: No`).
- Ресурс `pgsql` не промоутируется в Master.
- Ресурсы `vip`, `core-app-stack` и `daemon-svc` остаются в статусе **`Stopped`**.
- Данные защищены от перезаписи на отставшей копии.

## 5. Что делать при отклонении
1. Если `node2` все же промоутировался в Master в одиночку:
   - Проверить статус СУБД перед стартом: если база была остановлена штатно без рекавери-файла, она могла иметь статус `shut down`.
   - Проверить блок 4 скрипта `cluster-degraded-unblock.sh`.
