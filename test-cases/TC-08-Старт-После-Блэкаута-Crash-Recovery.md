# TC-08: Старт после блэкаута (Crash Recovery / Аварийный сброс)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-08`
- **MMD-диаграмма**: [`mmd/ХолодныйСтартМастераРезерваПослеПадения.mmd`](../mmd/ХолодныйСтартМастераРезерваПослеПадения.mmd)
- **Цель**: Проверить автоматическое восстановление кластера после внезапного полного обесточивания дата-центра (блэкаута), корректное определение режима `CRASH_RECOVERY`, сравнение LSN/таймлайнов агентом `pgsqlms`, выбор узла с наиболее свежими данными для промоута и догон репликации вторым узлом.
- **Объекты проверки**:
  - Распознавание состояния `in production` / `in crash recovery` утилитой `pg_controldata`.
  - Запись режима `MODE=CRASH_RECOVERY` в `/run/cluster_boot_mode`.
  - Механизм выбора мастера агентом `pgsqlms` (сравнение LSN точек фиксации WAL).
  - Наличие параметра `wal_log_hints = on` в `postgresql.conf`.

---

## 2. Предусловия
1. Кластер находился в рабочем состоянии под нагрузкой транзакций.
2. Оба сервера одновременно аварийно обесточены (отключение питания стойки или `echo b > /proc/sysrq-trigger` на обоих узлах одновременно).

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Одновременная подача питания
**Действие:**
Одновременно включить питание серверов `node1` и `node2`.

---

### Шаг 2. Контроль режима запуска в анализаторе
**Команда на обоих узлах после старта ОС:**
```bash
cat /run/cluster_boot_mode
```
**Ожидаемый результат:**
- На обоих узлах:
  ```text
  MODE=CRASH_RECOVERY
  DB_RAW_STATE=in production (на node1) / in archive recovery (на node2)
  UNBLOCK_TIMEOUT_SEC=900
  ```

---

### Шаг 3. Контроль согласования ролей СУБД в Pacemaker
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- Оба узла видят друг друга, кворум собран штатно (`Quorate: Yes`).
- Агент `pgsqlms` выполняет предстартовый опрос заголовков WAL:
  - Сравнивает LSN-позиции последней контрольной точки (`checkpoint REDO location`).
  - Присваивает больший вес (`master-score`) узлу `node1` (бывшему Master с самыми свежими данными).
- СУБД на `node1` промоутируется в `Master`.
- СУБД на `node2` догоняет поток WAL и переходит в статус синхронного `Slave` (`Unpromoted`).
- VIP и группа сервисов поднимаются на `node1`.
- Целостность данных полностью сохранена.

---

## 4. Что делать при отклонении
1. Если на обоих серверах статус базы оказался одинаковым, и Pacemaker не может выбрать узел для промоута:
   - Проверить значения LSN на обоих узлах:
     ```bash
     sudo -u postgres /usr/lib/postgresql/16/bin/pg_controldata /var/lib/postgresql/16/main | grep "REDO location"
     ```
   - Убедиться, что параметр `wal_log_hints = on` прописан в `postgresql.conf` на обоих узлах.
2. Сбросить зависшие состояния ресурсов:
   ```bash
   pcs resource cleanup pgsql
   ```
