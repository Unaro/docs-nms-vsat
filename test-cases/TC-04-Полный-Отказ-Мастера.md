# TC-04: Полный отказ узла Master (Node Crash / Double Failure)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-04`
- **MMD-диаграмма**: [`mmd/ПадениеApp1БД1.mmd`](../mmd/ПадениеApp1БД1.mmd)
- **Цель**: Проверить устойчивость кластера к катастрофическому отказу активного узла (`node1`): одновременная потеря связи по кольцам Corosync knet Ring 0 и Ring 1, подтверждение связи с внешним маршрутизатором через `ping-gateway`, аварийный промоут Standby СУБД на `node2`, подъем VIP и группы сервисов на единственном выжившем узле, переход в разрешённый деградированный режим (одиночная запись).
- **Объекты проверки**:
  - Детектирование потери узла по транспорту Corosync knet.
  - Ограничение размещения по внешнему арбитру (`location rule score=-INFINITY pingd lt 1`).
  - Перевод PostgreSQL на `node2` в Master (`pgsqlms promote`).
  - Рассылка GARP и перехват трафика маршрутизатором Eltex.
  - Работа системы в деградированном режиме (Single-node Primary).

---

## 2. Предусловия
1. Кластер находится в штатном режиме (`node1` — Master, `node2` — Standby).
2. На маршрутизаторе `192.168.1.1` активен ARP-кэш, указывающий VIP `192.168.1.100` на MAC-адрес `node1`.
3. Подготовлен скрипт или фоновый цикл записи данных через VIP для замера времени RTO/RPO:
   ```bash
   while true; do psql -h 192.168.1.100 -p 5000 -U haproxy_check -d postgres -c "INSERT INTO heartbeat_test (ts) VALUES (now());" 2>/dev/null && echo -n "." || echo -n "X"; sleep 1; done
   ```

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Имитация внезапного полного отключения узла node1
**Команда на `node1` (root):**
```bash
# Мгновенная перезагрузка без сброса дисков (имитация сбоя питания / kernel panic)
echo b > /proc/sysrq-trigger
```

### Шаг 2. Контроль потери связности и арбитража на node2
**Команда на `node2`:**
```bash
journalctl -u corosync -u pacemaker -f --no-tail
```
**Ожидаемый результат:**
1. Corosync фиксирует отключение линков:
   - `KNET: link: Resetting link id 0` (Ring 0)
   - `KNET: link: Resetting link id 1` (Ring 1)
   - `Membership: Node 1 left`
2. Ресурс `ping-gateway` подтверждает доступность маршрутизатора `192.168.1.1` (`pingd=100`).
3. Кластер переходит к выполнению failover на `node2`.

### Шаг 3. Контроль аварийного переключения ресурсов на node2
**Ожидаемый результат в журнале `node2`:**
1. `pgsqlms`: инициирует промоут локальной БД:
   `promoting PostgreSQL to master` -> `pg_ctl promote`
2. СУБД переходит в статус `Master (RW)`.
3. Запускается `vip` на интерфейсе `eth0` узла `node2`:
   `IPaddr2(vip)[...]: ... sending 5 gratuitous ARP for 192.168.1.100`
4. Запускается группа `app-stack`:
   - `systemd:haproxy`
   - `systemd:my-app`
   - `systemd:my-daemon`

### Шаг 4. Проверка состояния кластера командой pcs status
**Команда на `node2`:**
```bash
pcs status
```
**Ожидаемый результат:**
- `Node List`:
  - `node1: UNCLEAN (offline)`
  - `node2: Online`
- `Clone Set: pgsql-clone [pgsql] (promotable)`:
  - `Promoted: node2` (Master).
  - `Stopped: node1`.
- `Resource Group: app-stack`:
  - `vip`: Started `node2`.
  - `haproxy-svc`: Started `node2`.
  - `app-svc`: Started `node2`.
  - `daemon-svc`: Started `node2`.

### Шаг 5. Проверка сокета проверки роли и записи в СУБД
**Команда на `node2`:**
```bash
curl -i http://127.0.0.1:9200/
psql -h 127.0.0.1 -p 5000 -U haproxy_check -d postgres -c "SELECT inet_server_addr(), pg_is_in_recovery();"
```
**Ожидаемый результат:**
- Сокет :9200 отдаёт `HTTP 200 OK Master`.
- Запрос к порту 5000 успешен, `pg_is_in_recovery = f`.
- Фоновый цикл записи восстанавливает прохождение транзакций (RTO <= 20 секунд).
- Кластер полноценно работает в деградированном режиме на одном сервере.

---

## 4. Критерии успешности (Pass/Fail)
- **PASS**: При полном отключении `node1` узел `node2` автоматически взял на себя роли Master СУБД, VIP и сервисов приложения; Split-Brain не возник; простой сервиса записи не превысил 25 секунд.
- **FAIL**: Узел `node2` заблокировал промоут при наличии связи с роутером, либо VIP не поднялся, либо произошла потеря целостности базы данных.
