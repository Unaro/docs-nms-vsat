# TC-05: Одновременный холодный старт обоих узлов после отключения питания

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-05`
- **MMD-диаграмма**: [`mmd/ХолодныйСтартМастераРезерваПослеПадения.mmd`](../mmd/ХолодныйСтартМастераРезерваПослеПадения.mmd)
- **Цель**: Проверить процедуру предстартовой самодиагностики дисковой подсистемы сервисом `cluster-boot-analyzer`, одновременное согласование кворума Corosync knet по двум кольцам, сравнение LSN СУБД ресурсом `pgsqlms` и корректный промоут наиболее актуального узла в статус Master.
- **Объекты проверки**:
  - Юнит `cluster-boot-analyzer.service` и скрипт `cluster-boot-analyzer.sh`.
  - Проверка целостности каталога `$PGDATA`, прав RW и порога свободного места (`>= 5%`).
  - Corosync knet handshake по Ring 0 и Ring 1.
  - PAF `pgsqlms` Probe: автоматический выбор мастера по LSN.
  - Порядок запуска: сначала `vip`, затем `app-stack`.
  - Подключение второго узла в роли реплики Standby.

---

## 2. Предусловия
1. На обоих узлах настроен скрипт `bootstrap-ha.sh`.
2. Оба узла выключены (имитация полного обесточивания стойки / серверной).
3. Маршрутизатор `192.168.1.1` включен и доступен.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Подача питания и запуск серверов
**Действие:**
Одновременно включить питание на `node1` и `node2`.

### Шаг 2. Контроль работы cluster-boot-analyzer в системном журнале
**Команда на обоих узлах после загрузки:**
```bash
journalctl -u cluster-boot-analyzer.service --no-pager
cat /run/cluster_boot_mode
```
**Ожидаемый результат:**
- Сервис успешно отработал (`Finished Pre-flight Disk Health Check... status=0/SUCCESS`).
- В журнале зафиксировано:
  - Проверка `$PGDATA/PG_VERSION` пройдена.
  - Создание и удаление тестового файла `.cluster_rw_test` подтвердило доступность файловой системы на запись.
  - Свободного места более 5%.
- Файл `/run/cluster_boot_mode` сформирован и содержит режим запуска (`MODE=COLD_START` или `MODE=CRASH_RECOVERY`).
- Только после этого systemd дал разрешение на старт `corosync.service` и `pacemaker.service`.

### Шаг 3. Контроль согласования членства Corosync
**Команда на `node1` / `node2`:**
```bash
corosync-quorumtool -s
```
**Ожидаемый результат:**
- Обе ноды обнаружили друг друга по Ring 0 (`10.0.0.x`) и Ring 1 (`192.168.1.x`).
- `Quorate: Yes`, `Nodes: 2`.

### Шаг 4. Контроль выбора мастера агентом pgsqlms
**Команда на узлах:**
```bash
journalctl -u pacemaker | grep -E "pgsql.*(LSN|master-score|promoting)"
```
**Ожидаемый результат:**
1. Pacemaker выполняет операцию `probe` на обоих узлах.
2. Считываются текущие LSN из `pg_controldata`.
3. Узел с более продвинутым LSN (или первый ответивший при равенстве) получает `master-score = 1000`.
4. Отстающий узел получает `master-score = 100`.
5. Узел со счётом 1000 получает команду `promote` и становится Master.

### Шаг 5. Контроль запуска ресурсов
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- `Clone Set: pgsql-clone`: один узел `Promoted`, второй узел `Unpromoted`.
- `Resource Group: app-stack` (`vip`, `haproxy-svc`, `app-svc`, `daemon-svc`): активны на том же узле, где Promoted СУБД (благодаря colocation `500` и `INFINITY`).
- `ping-gateway-clone`: активен на обоих узлах.

### Шаг 6. Проверка проверки сокетов роли СУБД
**Команда на Master-узле:**
```bash
curl -i http://127.0.0.1:9200/
```
**Ожидаемый результат:** `HTTP/1.1 200 OK Master`

**Команда на Standby-узле:**
```bash
curl -i http://127.0.0.1:9200/
```
**Ожидаемый результат:** `HTTP/1.1 503 Service Unavailable Slave`

### Шаг 7. Проверка репликации WAL
**Команда на Master-узле:**
```bash
sudo -u postgres psql -c "SELECT client_addr, state, sync_state FROM pg_stat_replication;"
```
**Ожидаемый результат:**
- Присутствует строка со `state = streaming`, подтверждающая, что реплика подключилась к мастеру.

---

## 4. Негативный подтест: Блокировка старта при повреждении диска БД
**Действие на тестовом стенде:**
1. Перевести раздел `$PGDATA` в Read-Only:
   ```bash
   mount -o remount,ro /var/lib/postgresql
   systemctl restart cluster-boot-analyzer.service
   ```
**Ожидаемый результат:**
- `cluster-boot-analyzer.service` аварийно завершается с ошибкой (`exit 1`):
  `КРИТИЧЕСКАЯ ОШИБКА: Файловая система БД в режиме Read-Only! Старт Pacemaker заблокирован.`
- `corosync.service` и `pacemaker.service` НЕ запускаются (защищены зависимостью `RequiredBy`).
- Сбойный узел не входит в кластер и не может повредить данные.
- Восстановление: `mount -o remount,rw /var/lib/postgresql`.

---

## 5. Критерии успешности (Pass/Fail)
- **PASS**: При одновременном включении обоих серверов кластер автоматически собрал кворум, корректно определил Master по LSN, запустил VIP и службы, наладил потоковую репликацию без ручного вмешательства.
- **FAIL**: Возникновение Split-Brain, падение Corosync, пропуск предстартовых проверок дисков или незапуск репликации.
