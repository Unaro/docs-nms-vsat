# TC-02: Авария процесса PostgreSQL на узле Master

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-02`
- **MMD-диаграмма**: [`mmd/ПадениеБД1.mmd`](../mmd/ПадениеБД1.mmd)
- **Цель**: Проверить автоматическое обнаружение падения СУБД PostgreSQL на активном Master-узле (`node1`), корректный сброс TCP-сессий в HAProxy, промоут Standby-узла (`node2`) в статус Master ресурсом `pgsqlms`, а также миграцию Виртуального IP и группы сервисов `app-stack`.
- **Объекты проверки**:
  - Срабатывание сокета проверки роли `db-role-check` (:9200) и маркировка бэкенда `DOWN`.
  - Директива HAProxy `on-marked-down shutdown-sessions`.
  - Монитор `ocf:heartbeat:pgsqlms` (демоут упавшего узла, промоут резерва).
  - Colocation constraints: миграция VIP и `app-stack` за новым Master.
  - Рассылка GARP в сеть маршрутизатора Eltex.

---

## 2. Предусловия
1. Кластер находится в штатном режиме (выполнен `TC-01`).
2. `node1` является Master (Promoted), VIP `192.168.1.100` активен на `node1`.
3. Открыта тестовая постоянная сессия подключения к базе данных через VIP:
   ```bash
   psql -h 192.168.1.100 -p 5000 -U haproxy_check -d postgres
   ```

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Имитация аварийного падения PostgreSQL на node1
**Команда на `node1`:**
```bash
# Аварийное принудительное завершение всех процессов PostgreSQL
pkill -9 -e -f "postgres: " || kill -9 $(head -n 1 /var/lib/postgresql/16/main/postmaster.pid)
```

### Шаг 2. Проверка немедленной реакции HAProxy и сокета :9200
**Команда на `node1`:**
```bash
curl -i http://127.0.0.1:9200/
```
**Ожидаемый результат:**
- Сокет возвращает ошибку соединения (`curl: (7) Failed to connect` или HTTP 503).
- Ранее открытая клиентская сессия `psql` к порту 5000 мгновенно сбрасывается (`server closed the connection unexpectedly`) благодаря опции `on-marked-down shutdown-sessions`.

### Шаг 3. Контроль действий Pacemaker в журнале событий
**Команда на `node2`:**
```bash
journalctl -u pacemaker -f --no-tail
```
**Ожидаемый результат:**
1. В течение <= 15 секунд срабатывает мониторинг `pgsql_monitor`:
   `pgsql(pgsql-clone)[...]: ... Master is not running`
2. Pacemaker объявляет ресурс `pgsql` на `node1` сбойным.
3. Pacemaker инициирует промоут на `node2`:
   `pgsql(pgsql-clone)[...]: ... promoting PostgreSQL to master`
4. Срабатывают ограничения размещения:
   - `vip` останавливается на `node1` и поднимается на `node2`.
   - Группа `app-stack` (`haproxy-svc`, `app-svc`, `daemon-svc`) останавливается на `node1` и запускается на `node2`.

### Шаг 4. Проверка итогового статуса кластера
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- `Clone Set: pgsql-clone [pgsql] (promotable)`:
  - `Promoted: node2` (теперь Master!).
  - `Stopped: node1` (или Demoted / Failed).
- `Resource Group: app-stack`:
  - `vip`: Started `node2`.
  - `haproxy-svc`: Started `node2`.
  - `app-svc`: Started `node2`.
  - `daemon-svc`: Started `node2`.

### Шаг 5. Проверка сокета :9200 и HAProxy на node2
**Команда на `node2`:**
```bash
curl -i http://127.0.0.1:9200/
psql -h 127.0.0.1 -p 5000 -U haproxy_check -d postgres -c "SELECT inet_server_addr(), pg_is_in_recovery();"
```
**Ожидаемый результат:**
- Сокет `127.0.0.1:9200` отдаёт:
  ```http
  HTTP/1.1 200 OK
  Master
  ```
- Запрос к порту 5000 возвращает `pg_is_in_recovery = f`. Запись в базу данных через локальный HAProxy на `node2` работает корректно.

### Шаг 6. Проверка доступности сервиса через VIP
**Команда с внешней рабочей станции / тестового клиента:**
```bash
arping -c 2 -I eth0 192.168.1.100
psql -h 192.168.1.100 -p 5000 -U haproxy_check -d postgres -c "CREATE TABLE IF NOT EXISTS failover_test (id serial, t timestamp default now()); INSERT INTO failover_test DEFAULT VALUES; SELECT count(*) FROM failover_test;"
```
**Ожидаемый результат:**
- ARP-запрос подтверждает, что VIP привязан к MAC-адресу интерфейса `node2`.
- Транзакция записи через VIP завершается успехом.

---

## 4. Восстановление исходного состояния (Teardown)
```bash
# 1. Запустить PostgreSQL на node1 через Pacemaker после устранения аварии
pcs resource cleanup pgsql
# 2. Дождаться, пока node1 подключится в качестве Standby реплики
pcs status
```

---

## 5. Критерии успешности (Pass/Fail)
- **PASS**: Переключение на `node2` произошло автоматически за время не более 35 секунд (таймаут монитора СУБД + промоут + запуск стека). Висячие сессии сброшены, данные не повреждены, запись доступна на новом мастере.
- **FAIL**: Зависание промоута, возникновение Split-Brain (два узла считают себя мастером) или VIP остался на узле со сбойной СУБД.
