# TC-04: Отказ только СУБД на node1 (Проксирование через интерконнект)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-04`
- **MMD-диаграмма**: [`mmd/ПадениеБД1.mmd`](../mmd/ПадениеБД1.mmd)
- **Цель**: Проверить локализацию сбоя при отказе СУБД на активном узле: БД на `node2` промоутируется в `Master`, а прикладной стек (`VIP`, `HAProxy`, демоны) **остается на `node1` без рестарта**, при этом HAProxy прозрачно перенаправляет запросы в БД2 по интерконнекту Ring 0 (`10.0.0.2`).
- **Объекты проверки**:
  - Агент СУБД `pgsqlms` (демоут на `node1`, промоут на `node2`).
  - Ограничение связи `pcs constraint colocation add vip with master pgsql-clone 500` (мягкая рекомендация 500 вместо жесткого INFINITY).
  - Балансировщик HAProxy на порту 5000: переключение активного бэкенда с `node1_db_r0` на `node2_db_r0`.
  - Сокет проверки роли СУБД `:9200`.

---

## 2. Предусловия
1. Кластер находится в базовом состоянии (`TC-01`).
2. `node1` является Master, `node2` — Standby.
3. Доступно подключение через локальный HAProxy:
   ```bash
   psql -h 127.0.0.1 -p 5000 -U postgres -d postgres -c "SELECT pg_is_in_recovery();"
   # Ожидается: 'f'
   ```

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Имитация отказа СУБД на node1
**Команда на `node1`:**
```bash
# Запрещаем запуск СУБД на node1 через команду ban или принудительно гасим процесс:
pcs resource ban pgsql node1
```

---

### Шаг 2. Контроль статуса ресурсов кластера
**Команда на `node1` / `node2`:**
```bash
pcs status
```
**Ожидаемый результат:**
- `Clone Set: pgsql-clone [pgsql] (promotable)`:
  - `Promoted: node2` (БД на `node2` стала Master).
  - `Stopped: [ node1 ]` (на `node1` ресурс СУБД остановлен).
- **Критический результат**: Ресурсы `vip`, `core-app-stack` (`haproxy-svc`, `app-svc`) и `daemon-svc` **остаются в статусе Started на `node1` без перезапуска**.

---

### Шаг 3. Проверка прозрачного проксирования HAProxy на удаленный Master
**Команда на `node1`:**
```bash
psql -h 127.0.0.1 -p 5000 -U postgres -d postgres -c "SELECT inet_server_addr(), pg_is_in_recovery();"
```
**Ожидаемый результат:**
- Запрос выполняется успешно.
- `inet_server_addr()` возвращает `10.0.0.2` (IP-адрес СУБД Сервера 2 в Ring 0).
- `pg_is_in_recovery()` возвращает `f` (база принимает транзакции на запись).
- Приложение на `node1` продолжает непрерывно работать с БД без потери сессий.

---

## 4. Восстановление исходного состояния
```bash
# Снимаем запрет на запуск СУБД на node1:
pcs resource clear pgsql node1
pcs resource cleanup pgsql

# Проверяем, что node1 подключился в роли Slave:
pcs status | grep -E "Promoted:|Unpromoted:"
# Ожидается: Promoted: node2, Unpromoted: node1
```

---

## 5. Что делать при отклонении
1. Если HAProxy не переключился на `node2`:
   - Проверить статус бэкендов в HAProxy:
     ```bash
     journalctl -u haproxy -n 30 --no-pager
     ```
   - Проверить отклик сокета `:9200` на втором сервере:
     ```bash
     curl -i http://10.0.0.2:9200/
     # Ожидается: HTTP/1.1 200 OK Master
     ```
2. Если `vip` и приложение уехали вслед за базой на `node2`:
   - Проверить силу связи colocation между VIP и БД:
     ```bash
     pcs constraint show --full
     ```
   - Правило должно иметь вес `500` (рекомендация), а не `INFINITY` (жесткая привязка).
