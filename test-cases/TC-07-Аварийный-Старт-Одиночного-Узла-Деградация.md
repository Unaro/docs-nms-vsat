# TC-07: Запуск одиночного узла в режиме деградации (Degraded Mode Unblock)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-07`
- **MMD-диаграмма**: [`mmd/ВосстановлениеПослеПаденияМастерРезерв.mmd`](../mmd/ВосстановлениеПослеПаденияМастерРезерв.mmd)
- **Цель**: Проверить работу расширенного 4-ступенчатого алгоритма сторожевого выхода в деградированный режим при старте одного узла без соседа:
  1. Валидация режима в `cluster-boot-analyzer.sh`.
  2. Запуск таймера `cluster-degraded-unblock.timer` с асимметричным сдвигом (на `node2` добавляется +120 сек для исключения одновременного промоута при сетевом разделении).
  3. Отработка **Предохранителя №1**: проверка доступности хотя бы одного шлюза из списка `ROUTER_IPS`.
  4. Отработка **Предохранителя №2**: проверка отсутствия соседа как по ICMP, так и по TCP-портам (9200, 5432, 22) на обоих кольцах (Ring 0 и Ring 1).
  5. Отработка **Предохранителя №3**: проверка отсутствия дубликата `CLUSTER_VIP` в сети через ping и `arping -D` (защита от Split-Brain и долгого fsck на соседе).
  6. Отработка **Предохранителя №4**: проверка статуса БД до аварии по `pg_controldata` (`in production`) или маркеру (`LAST_ROLE=MASTER`).
  7. Снятие блокировки кворума командой `pcs quorum unblock --yes` и успешный запуск сервисов.
  8. Проверка блокировки промоута, если одиночный узел был репликой.
- **Объекты проверки**:
  - Скрипты `/usr/local/sbin/cluster-boot-analyzer.sh` и `/usr/local/sbin/cluster-degraded-unblock.sh` (v2.0).
  - Юниты `cluster-degraded-unblock.timer` и `cluster-degraded-unblock.service`.
  - Защита от Split-Brain, TCP-сканирование и запрет промоута реплики в одиночку.

---

## 2. Предусловия
1. На стенде настроен обновленный скрипт `bootstrap-ha.sh` (v2.0).
2. `node2` гарантированно выключен или изолирован (кабели Ring 0 и Ring 1 отключены).
3. Маршрутизаторы из `ROUTER_IPS` (`192.168.1.1`, `192.168.1.2`) включены и доступны с `node1`.
4. Для сокращения времени проведения теста на `node1` в `/etc/default/ha-cluster` временно установлен ускоренный таймаут:
   ```bash
   sed -i 's/CRASH_TIMEOUT_SEC="900"/CRASH_TIMEOUT_SEC="20"/' /etc/default/ha-cluster
   sed -i 's/COLD_START_TIMEOUT_SEC="180"/COLD_START_TIMEOUT_SEC="20"/' /etc/default/ha-cluster
   sed -i 's/NODE2_ASYMMETRIC_DELAY_SEC="120"/NODE2_ASYMMETRIC_DELAY_SEC="10"/' /etc/default/ha-cluster
   ```

## 3. Шаги выполнения: Сценарий А (Позитивный — Старт бывшего Мастера)

### Шаг А1. Подготовка узла node1 как бывшего Master
**Действие на `node1`:**
Убедиться, что в `pg_controldata /var/lib/postgresql/16/main` статус СУБД равен `in production` (или `shut down in recovery = no`).
Имитировать аварийное выключение/перезагрузку:
```bash
reboot
```

### Шаг А2. Контроль работы cluster-boot-analyzer при загрузке
**Команда на `node1` после старта ОС:**
```bash
cat /run/cluster_boot_mode
```
**Ожидаемый результат:**
- `MODE=CRASH_RECOVERY`
- `DB_RAW_STATE=in production`
- `UNBLOCK_TIMEOUT_SEC=20`

### Шаг А3. Контроль первоначальной блокировки Pacemaker
**Команда на `node1` в первые секунды после старта:**
```bash
pcs status
```
**Ожидаемый результат:**
- `corosync` не видит соседа: `Quorate: No`.
- Из-за политики `no-quorum-policy=stop` все ресурсы находятся в состоянии `Stopped` (или заблокированы).

### Шаг А4. Контроль работы 4 предохранителей в cluster-degraded-unblock.sh
**Команда на `node1`:**
```bash
journalctl -u cluster-degraded-unblock.service -f --no-tail
```
**Ожидаемый результат по истечении таймаута (20 сек):**
1. Скрипт просыпается и проверяет кворум: `Quorate: No`.
2. **Предохранитель №1 (Шлюзы)**:
   - Проверяются IP из `ROUTER_IPS` (`192.168.1.1`, `192.168.1.2`).
   - Хотя бы один шлюз отвечает.
3. **Предохранитель №2 (Сосед по ICMP и TCP)**:
   - `ping` по Ring 0 (`10.0.0.2`) и Ring 1 (`192.168.1.12`) -> 100% loss.
   - Проверка TCP-портов 9200, 5432, 22 через `/dev/tcp` завершается по таймауту (сосед не отвечает по сети).
4. **Предохранитель №3 (Проверка CLUSTER_VIP)**:
   - `arping -D -I eth0 192.168.1.100` подтверждает, что VIP не занят другим узлом в сети.
5. **Предохранитель №4 (Статус БД)**:
   - `DB_RAW_STATE == "in production"` -> подтверждено, что узел был Master.
   - В логе: `cluster-watchdog: Аварийный старт: локальная БД была Master. Активация режима деградации.`
6. Выполняется команда: `pcs quorum unblock --yes`.

### Шаг А5. Проверка автоматического запуска сервисов после разблокировки
**Команда на `node1`:**
```bash
pcs status
```
**Ожидаемый результат:**
- `pgsql`: переведён в `Promoted: node1` (Master).
- `vip`: `Started node1` (192.168.1.100 поднят на eth0).
- `app-stack` (`haproxy-svc`, `app-svc`, `daemon-svc`): `Started node1`.
- Сокет `curl http://127.0.0.1:9200/` отдаёт `HTTP 200 OK Master`.
- Подключение к `127.0.0.1:5000` и `192.168.1.100:5000` успешно, база принимает запись.

## 4. Шаги выполнения: Сценарий Б (Негативный — Блокировка одиночной Реплики)

### Шаг Б1. Подготовка узла, бывшего репликой (Standby)
**Действие на тестовом узле `node2`:**
1. Задать статус СУБД в `/run/cluster_boot_mode`:
   ```bash
   echo "MODE=CRASH_RECOVERY" > /run/cluster_boot_mode
   echo "DB_RAW_STATE=in archive recovery" >> /run/cluster_boot_mode
   echo "UNBLOCK_TIMEOUT_SEC=5" >> /run/cluster_boot_mode
   ```
2. Запустить скрипт деградации:
   ```bash
   /usr/local/sbin/cluster-degraded-unblock.sh
   ```

### Шаг Б2. Контроль срабатывания блокировки
**Команда:**
```bash
journalctl -t cluster-watchdog -n 20
```
**Ожидаемый результат:**
- Скрипт обнаруживает, что СУБД до сбоя была репликой.
- В системный журнал пишется сообщение:
  `cluster-watchdog: СТОП: Узел не был подтвержденным Master (MODE=CRASH_RECOVERY, ROLE=UNKNOWN, DB=in archive recovery).`
- Скрипт завершается с ошибкой (`exit 1`).
- Команда `pcs quorum unblock` **НЕ вызывается**! Ресурсы остаются в безопасном остановленном состоянии.

## 5. Шаги выполнения: Сценарий В (Предохранитель активного VIP / Split-Brain)
**Действие:**
Поднять тестовый адрес `192.168.1.100` на стороннем хосте или симулировать его активность.
Запустить скрипт деградации: `/usr/local/sbin/cluster-degraded-unblock.sh`.

**Ожидаемый результат:**
- Предохранитель №3 фиксирует ответ от VIP в сети:
  `cluster-watchdog: КРИТИЧЕСКАЯ ОШИБКА: Виртуальный IP (192.168.1.100) УЖЕ АКТИВЕН в сети! Защита от Split-Brain сработала.`
- Завершение с кодом `exit 1`. Разблокировка отменена, Split-Brain предотвращен!

## 7. Критерии успешности (Pass/Fail)
- **PASS**:
  - Бывший мастер успешно разблокировал кворум после прохождения всех 4 предохранителей (шлюзы, ICMP/TCP соседа, arping VIP, роль Master).
  - Бывшая реплика заблокировала промоут и предотвратила рассинхронизацию данных.
  - При обнаружении занятого VIP разблокировка немедленно отменяется.
- **FAIL**: Несанкционированный промоут реплики, промоут при занятом VIP или ложная блокировка мастера.
