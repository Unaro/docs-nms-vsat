# TC-07: Запуск одиночного узла в режиме деградации (Degraded Mode Unblock)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-07`
- **MMD-диаграмма**: [`mmd/ВосстановлениеПослеПаденияМастерРезерв.mmd`](../mmd/ВосстановлениеПослеПаденияМастерРезерв.mmd)
- **Цель**: Проверить работу алгоритма сторожевого выхода в деградированный режим при старте одного узла без соседа:
  1. Валидация режима в `cluster-boot-analyzer.sh`.
  2. Запуск таймера `cluster-degraded-unblock.timer`.
  3. Отработка предохранителя №1 (проверка доступности роутера и подтверждение отсутствия соседа по ICMP).
  4. Отработка предохранителя №2 (проверка роли СУБД перед аварией по `pg_controldata` / маркеру).
  5. Снятие блокировки кворума командой `pcs quorum unblock --yes` и успешный запуск сервисов.
  6. Проверка блокировки промоута, если одиночный узел был репликой.
- **Объекты проверки**:
  - Скрипты `/usr/local/sbin/cluster-boot-analyzer.sh` и `/usr/local/sbin/cluster-degraded-unblock.sh`.
  - Юниты `cluster-degraded-unblock.timer` и `cluster-degraded-unblock.service`.
  - Защита от Split-Brain и запрет промоута реплики в одиночку.

---

## 2. Предусловия
1. На стенде настроен скрипт `bootstrap-ha.sh`.
2. `node2` гарантированно выключен или изолирован (кабели Ring 0 и Ring 1 отключены).
3. Маршрутизатор `192.168.1.1` включен и доступен с `node1`.
4. Для сокращения времени проведения теста на `node1` в `/etc/default/ha-cluster` временно установлен ускоренный таймаут:
   ```bash
   sed -i 's/CRASH_TIMEOUT_SEC="900"/CRASH_TIMEOUT_SEC="20"/' /etc/default/ha-cluster
   sed -i 's/COLD_START_TIMEOUT_SEC="180"/COLD_START_TIMEOUT_SEC="20"/' /etc/default/ha-cluster
   ```

---

## 3. Шаги выполнения: Сценарий А (Позитивный — Старт бывшего Мастера)

### Шаг А1. Подготовка узла node1 как бывшего Master
**Действие на `node1`:**
Убедиться, что в `pg_controldata /var/lib/postgresql/16/main` статус СУБД равен `in production` (или `shut down in recovery = no`).
Имитировать аварийное выключение/перезагрузку:
```bash
reboot
```

### Шаг А2. Контроль работы cluster-boot-analyzer при загрузке
**Команда на `node1` после старта ОС:**
```bash
cat /run/cluster_boot_mode
```
**Ожидаемый результат:**
- `MODE=CRASH_RECOVERY`
- `DB_RAW_STATE=in production`
- `UNBLOCK_TIMEOUT_SEC=20`

### Шаг А3. Контроль первоначальной блокировки Pacemaker
**Команда на `node1` в первые секунды после старта:**
```bash
pcs status
```
**Ожидаемый результат:**
- `corosync` не видит соседа: `Quorate: No`.
- Из-за политики `no-quorum-policy=stop` все ресурсы находятся в состоянии `Stopped` (или заблокированы).

### Шаг А4. Контроль работы cluster-degraded-unblock.sh
**Команда на `node1`:**
```bash
journalctl -u cluster-degraded-unblock.service -f --no-tail
```
**Ожидаемый результат по истечении таймаута (20 сек):**
1. Скрипт просыпается и проверяет кворум: `Quorate: No`.
2. **Предохранитель №1**:
   - `ping -c 3 192.168.1.1` -> Успешно (Маршрутизатор доступен).
   - `ping 10.0.0.2` и `ping 192.168.1.12` -> 100% loss (Сосед молчит).
3. **Предохранитель №2**:
   - `DB_RAW_STATE == "in production"` -> подтверждено, что узел был Master.
   - В логе: `cluster-watchdog: АВАРИЙНЫЙ СТАРТ: Сосед не встал. Локальная БД была Master. Активация режима деградации!`
4. Выполняется команда: `pcs quorum unblock --yes`.

### Шаг А5. Проверка автоматического запуска сервисов после разблокировки
**Команда на `node1`:**
```bash
pcs status
```
**Ожидаемый результат:**
- `pgsql`: переведён в `Promoted: node1` (Master).
- `vip`: `Started node1` (192.168.1.100 поднят на eth0).
- `app-stack` (`haproxy-svc`, `app-svc`, `daemon-svc`): `Started node1`.
- Сокет `curl http://127.0.0.1:9200/` отдаёт `HTTP 200 OK Master`.
- Подключение к `127.0.0.1:5000` и `192.168.1.100:5000` успешно, база принимает запись.

---

## 4. Шаги выполнения: Сценарий Б (Негативный — Блокировка одиночной Реплики)

### Шаг Б1. Подготовка узла, бывшего репликой (Standby)
**Действие на тестовом узле `node2`:**
1. Искусственно задать статус СУБД в `pg_controldata` как `in archive recovery` или записать в `/run/cluster_boot_mode`:
   ```bash
   echo "MODE=CRASH_RECOVERY" > /run/cluster_boot_mode
   echo "DB_RAW_STATE=in archive recovery" >> /run/cluster_boot_mode
   echo "UNBLOCK_TIMEOUT_SEC=5" >> /run/cluster_boot_mode
   ```
2. Запустить скрипт деградации:
   ```bash
   /usr/local/sbin/cluster-degraded-unblock.sh
   ```

### Шаг Б2. Контроль срабатывания блокировки
**Команда:**
```bash
journalctl -t cluster-watchdog -n 20
```
**Ожидаемый результат:**
- Скрипт обнаруживает, что СУБД до сбоя была репликой.
- В системный журнал пишется сообщение:
  `cluster-watchdog: СТОП! Этот узел до аварии был РЕПЛИКОЙ (in archive recovery). Автопромоут запрещен!`
- Скрипт завершается с ошибкой (`exit 1`).
- Команда `pcs quorum unblock` **НЕ вызывается**!
- Ресурсы остаются в безопасном остановленном состоянии, предотвращая порчу данных устаревшей репликой.

---

## 5. Шаги выполнения: Сценарий В (Предохранитель сетевой изоляции)
**Действие:**
Отключить линк к маршрутизатору `192.168.1.1` (`ip link set eth0 down`).
Запустить скрипт деградации: `/usr/local/sbin/cluster-degraded-unblock.sh`.

**Ожидаемый результат:**
- Скрипт фиксирует:
  `cluster-watchdog: ОШИБКА: Маршрутизатор (192.168.1.1) недоступен! Отмена разблокировки во избежание Split-Brain.`
- Завершение с кодом `exit 1`. Разблокировка отменена.

## 7. Критерии успешности (Pass/Fail)
- **PASS**:
  - Бывший мастер успешно разблокировал кворум и поднял сервис после проверки связи с роутером и тишины соседа.
  - Бывшая реплика заблокировала промоут и предотвратила потерю/рассинхронизацию данных.
  - При отсутствии связи со шлюзом разблокировка запрещена.
- **FAIL**: Несанкционированный промоут реплики, промоут при изолированном роутере, либо отказ разблокировки мастера.
