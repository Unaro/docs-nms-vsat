# TC-03: Сбой сервиса приложения или демона на узле с VIP

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-03`
- **MMD-диаграмма**: [`mmd/ПадениеApp1.mmd`](../mmd/ПадениеApp1.mmd)
- **Цель**: Проверить устойчивость кластера к локальному сбою сервисов приложения (`my-app` или `my-daemon`). Убедиться, что при сохранении исправности СУБД на `node1` группа `app-stack` и VIP безопасно мигрируют на `node2`, а балансировщик HAProxy на `node2` автоматически маршрутизирует прикладной SQL-трафик через межузловой линк Ring 0 на действующий Master на `node1`.
- **Объекты проверки**:
  - Мониторинг systemd-сервисов в Pacemaker (`app-svc`, `daemon-svc`).
  - Colocation-правило: `colocation add app-stack with vip INFINITY`.
  - Сохранение роли Master за `node1` (отсутствие ненужного failover базы данных).
  - Работа удалённой маршрутизации HAProxy через прямое соединение Ring 0 (`10.0.0.1:5432`).

---

## 2. Предусловия
1. Кластер находится в штатном режиме (`node1` — Master БД, VIP и `app-stack` запущены на `node1`).
2. Сетевое кольцо Ring 0 (`10.0.0.1` <-> `10.0.0.2`) исправно.
3. Сервисы `my-app` и `my-daemon` активны.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Имитация аварии прикладного процесса на node1
**Команда на `node1`:**
```bash
# Имитация зависания или падения процесса приложения
pkill -9 -e -f "my-app"
```

### Шаг 2. Контроль реакции Pacemaker
**Команда на `node1` / `node2`:**
```bash
journalctl -u pacemaker -f --no-tail
```
**Ожидаемый результат:**
1. Pacemaker фиксирует ошибку мониторинга:
   `app-svc_monitor_10000 on node1 'not running' (7)`
2. Pacemaker останавливает сбойную группу `app-stack` на `node1`:
   - остановка `daemon-svc`
   - остановка `app-svc`
   - остановка `haproxy-svc`
   - снятие `vip` с интерфейса `eth0` узла `node1`
3. Pacemaker поднимает группу на `node2`:
   - подъем `vip` на `node2`
   - запуск `haproxy-svc` на `node2`
   - запуск `app-svc` и `daemon-svc` на `node2`

### Шаг 3. Проверка статуса ресурсов и ролей СУБД
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- `Clone Set: pgsql-clone [pgsql] (promotable)`:
  - `Promoted: node1` (Master остался на `node1`!).
  - `Unpromoted: node2` (Standby остался на `node2`!).
- `Resource Group: app-stack`:
  - `vip`: Started `node2`.
  - `haproxy-svc`: Started `node2`.
  - `app-svc`: Started `node2`.
  - `daemon-svc`: Started `node2`.

### Шаг 4. Проверка опроса роли СУБД балансировщиком HAProxy на node2
**Команда на `node2`:**
```bash
# Проверка сокетов :9200
curl -s http://10.0.0.1:9200/
curl -s http://127.0.0.1:9200/
```
**Ожидаемый результат:**
- Запрос к `10.0.0.1:9200` (Ring 0 к `node1`) отдаёт `HTTP 200 OK Master`.
- Запрос к `127.0.0.1:9200` (локальный `node2`) отдаёт `HTTP 503 Service Unavailable Slave`.

### Шаг 5. Проверка сквозной передачи SQL-трафика через HAProxy2 на Master node1
**Команда на `node2` (или от лица my-app):**
```bash
psql -h 127.0.0.1 -p 5000 -U haproxy_check -d postgres -c "SELECT inet_server_addr(), pg_is_in_recovery();"
```
**Ожидаемый результат:**
- Запрос выполнен успешно.
- `inet_server_addr` показывает `10.0.0.1` (балансировщик `node2` отправил запрос по прямому линку на Master СУБД узла `node1`).
- `pg_is_in_recovery` равно `f` (транзакции записи доступны).

---

## 4. Восстановление исходного состояния (Teardown)
```bash
# Сбросить ошибки ресурса app-svc после устранения сбоя
pcs resource cleanup app-svc
# Проверить статус кластера
pcs status
```

---

## 5. Критерии успешности (Pass/Fail)
- **PASS**: VIP и сервисы мигрировали на `node2` за время не более 15 секунд; роль Master СУБД на `node1` не подверглась ложному переключению; приложение на `node2` успешно пишет в БД через HAProxy по интерконнекту Ring 0.
- **FAIL**: Зависание группы `app-stack`, падение репликации или возникновение ложного промоута СУБД на втором узле.
