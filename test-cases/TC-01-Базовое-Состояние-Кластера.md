# TC-01: Базовое состояние кластера

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-01`
- **MMD-диаграмма**: [`mmd/ШтатныйРежим.mmd`](../mmd/ШтатныйРежим.mmd)
- **Цель**: Проверить готовность и корректность функционирования всех компонентов кластера высокой доступности в нормальном сбалансированном состоянии (Node1 — Master, Node2 — Standby).
- **Объекты проверки**:
  - Транспорт Corosync Knet по двум кольцам (Ring 0, Ring 1).
  - Атрибут сетевого арбитра `pingd = 1` (мониторинг шлюза `192.168.1.1`).
  - Статус СУБД PostgreSQL 16 (`Promoted: node1`, `Unpromoted: node2`).
  - Размещение Виртуального IP (`192.168.1.100`), балансировщика HAProxy и группы сервисов.

---

## 2. Предусловия
1. Скрипт `bootstrap-ha.sh` выполнен на `node1` и `node2`.
2. Кластер инициализирован командой `bootstrap-ha.sh --init-pcs` на `node1`.
3. Сеть настроена:
   - `node1`: Ring 0 = `10.0.0.1`, Ring 1 = `192.168.1.11`
   - `node2`: Ring 0 = `10.0.0.2`, Ring 1 = `192.168.1.12`
   - Шлюз `192.168.1.1` доступен по ICMP.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Проверка состояния межузловой связи Corosync Knet
**Команда на обоих узлах:**
```bash
corosync-cfgtool -s
```
**Ожидаемый результат:**
- `LINK ID 0`: `addr = 10.0.0.x`, статус `connected`, `enabled`.
- `LINK ID 1`: `addr = 192.168.1.1x`, статус `connected`, `enabled`.
- Оба кольца активны без ошибок.

---

### Шаг 2. Проверка кворума и атрибута арбитра pingd
**Команда на любом узле:**
```bash
crm_mon -1 -A
```
**Ожидаемый результат:**
- `Quorate: Yes`.
- В секции Node Attributes отображается:
  - `node1: pingd=1000` (или `pingd=1`).
  - `node2: pingd=1000` (или `pingd=1`).

---

### Шаг 3. Проверка статуса ресурсов кластера
**Команда на `node1`:**
```bash
pcs status
```
**Ожидаемый результат:**
- Кластер в статусе `Ok`.
- `Clone Set: ping-gateway-clone`: активен на `node1` и `node2`.
- `Clone Set: pgsql-clone [pgsql] (promotable)`:
  - `Promoted: node1` (Master).
  - `Unpromoted: node2` (Slave / Standby).
- Ресурсы `vip`, `haproxy-svc`, `app-svc` (в группе `core-app-stack`) и `daemon-svc` запущены на `node1`.
- Сокет `db-role-check.socket` (:9200) отдает `HTTP/1.1 200 OK Master` на `node1` и `HTTP/1.1 503 Service Unavailable Slave` на `node2`.

---

## 4. Что делать при отклонении
1. Выполнить сброс возможных временных ошибок ресурсов:
   ```bash
   pcs resource cleanup
   ```
2. Проверить сетевую связность интерфейсов (`ip a`) и пинг до шлюза:
   ```bash
   ping -c 2 192.168.1.1
   ping -c 2 10.0.0.2
   ```
3. Проверить журнал событий кластера:
   ```bash
   journalctl -u pacemaker -u corosync -n 50 --no-pager
   ```
4. Если СУБД на `node2` не встает в режим Standby, проверить доступность слота репликации и файл `.pgpass`:
   ```bash
   sudo -u postgres PGPASSFILE=/var/lib/postgresql/.pgpass psql -h 10.0.0.1 -p 5432 -U repl_user -d postgres -c "IDENTIFY_SYSTEM;"
   ```
