# TC-03: Потеря связи с роутером (Сетевой арбитр)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-03`
- **MMD-диаграмма**: [`mmd/ШтатныйРежим.mmd`](../mmd/ШтатныйРежим.mmd)
- **Цель**: Проверить реакцию кластера на потерю связности активного узла с внешним маршрутизатором (выступающим в роли псевдо-арбитра), корректное обнуление атрибута `pingd` и плановый перенос ресурсов на второй узел, имеющий доступ к сети клиентов.
- **Объекты проверки**:
  - Ресурс мониторинга `ping-gateway` (`ocf:pacemaker:ping`).
  - Правила размещения ресурсов по атрибуту `pingd`:
    - `pcs constraint location vip rule score-attribute=pingd pingd gt 0`
    - `pcs constraint location pgsql-clone rule role=Master score-attribute=pingd pingd gt 0`
  - Миграция VIP, Master-роли СУБД и прикладного стека на `node2`.

---

## 2. Предусловия
1. Кластер находится в базовом состоянии (`TC-01`).
2. Ресурсы запущены на `node1`.
3. Маршрутизатор `192.168.1.1` доступен с обоих серверов (`pingd = 1000` / `1`).

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Блокировка трафика к маршрутизатору на node1
**Команда на `node1`:**
```bash
iptables -I OUTPUT 1 -d 192.168.1.1 -j DROP
```

---

### Шаг 2. Контроль изменения атрибута pingd
**Команда на `node1` / `node2`:**
```bash
# Ждем срабатывания монитора ping-gateway (интервал 5с + dampen 10с = ~15с):
crm_mon -1 -A
```
**Ожидаемый результат:**
- В секции Node Attributes фиксируется:
  - `node1: pingd=0` (связь с внешним миром потеряна).
  - `node2: pingd=1000` (связь со шлюзом активна).

---

### Шаг 3. Контроль перемещения ресурсов кластера
**Команда на `node2`:**
```bash
pcs status
```
**Ожидаемый результат:**
- Pacemaker фиксирует, что `node1` больше не удовлетворяет правилу `pingd gt 0`.
- Происходит автоматический и плавный перенос:
  - СУБД на `node1` переводится в `Slave`, а на `node2` промоутируется в `Master`.
  - Ресурсы `vip`, `core-app-stack` и `daemon-svc` останавливаются на `node1` и запускаются на `node2`.
- Клиентский трафик перенаправляется на `node2`.

---

## 4. Восстановление исходного состояния
```bash
# На node1 удаляем блокирующее правило iptables:
iptables -D OUTPUT -d 192.168.1.1 -j DROP

# Ждем восстановления атрибута pingd:
crm_mon -1 -A
# Ожидается: node1: pingd=1000
# Благодаря resource-stickiness=100 ресурсы остаются на node2 без паразитного отката назад.
```

---

## 5. Что делать при отклонении
1. Если ресурсы не мигрировали на `node2`:
   - Проверить наличие правил размещения `location` в конфигурации кластера:
     ```bash
     pcs constraint show --full
     ```
   - Должны присутствовать правила:
     ```text
     Location Constraints:
       Resource: vip
         Rule: boolean-op=and score-attribute=pingd (expression: pingd gt 0)
       Resource: pgsql-clone
         Rule: role=Master score-attribute=pingd (expression: pingd gt 0)
     ```
2. Если `pingd` не падает в 0:
   - Проверить список адресов в `ROUTER_IPS` (`/etc/default/ha-cluster`). Если там указано несколько IP, заблокировать все адреса маршрутизаторов.
