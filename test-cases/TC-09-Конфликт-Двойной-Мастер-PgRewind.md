# TC-09: Конфликт «Двойной Master» (Timeline Divergence и pg_rewind)

## 1. Паспорт тест-кейса
- **Идентификатор**: `TC-09`
- **MMD-диаграмма**: [`mmd/ВосстановлениеПослеПаденияМастер.mmd`](../mmd/ВосстановлениеПослеПаденияМастер.mmd)
- **Цель**: Проверить автоматическое разрешение конфликта расхождения таймлайнов WAL (когда на обоих узлах в разное время производилась запись), выбор узла с наиболее актуальными транзакциями, запуск утилиты `pg_rewind` на отставшем узле и возврат его в кластер в качестве реплики.
- **Объекты проверки**:
  - Механизм `pg_rewind` (откатка локальных страниц до общей точки ветвления таймлайнов).
  - Параметры PostgreSQL `wal_log_hints = on` и `track_commit_timestamp = on`.
  - Беспарольная аутентификация пользователя `repl_user` через `.pgpass`.
  - Автоматизация процесса через OCF-агент `pgsqlms`.

---

## 2. Предусловия
1. Кластер находился в базовом состоянии (`TC-01`), `node1` — Master.
2. Файл `.pgpass` на обоих серверах настроен и имеет права `0600`.
3. Параметр `wal_log_hints = on` включен в `postgresql.conf`.

---

## 3. Шаги выполнения и ожидаемые результаты

### Шаг 1. Формирование расхождения истории транзакций
**Действие:**
1. Штатно остановить `node1`:
   ```bash
   pcs cluster stop node1
   ```
2. Убедиться, что `node2` стал Master (`Promoted: node2`).
3. Записать новую транзакцию на `node2`:
   ```bash
   psql -p 5432 -U postgres -d postgres -c "CREATE TABLE test_divergence (id int, val text); INSERT INTO test_divergence VALUES (1, 'node2_data');"
   ```
4. Аварийно обесточить `node2`:
   ```bash
   echo b > /proc/sysrq-trigger
   ```

---

### Шаг 2. Одновременный запуск обоих узлов
**Действие:**
Включить питание обоих серверов одновременно.

---

### Шаг 3. Контроль разрешения конфликта в Pacemaker
**Команда на любом узле:**
```bash
pcs status
```
**Ожидаемый результат:**
- Агент СУБД определяет, что на `node2` открыт более старший номер таймлайна (Timeline 2) и зафиксирован более поздний LSN.
- `node2` промоутируется в `Master`.
- На `node1` агент автоматически вызывает `pg_rewind --target-pgdata=$PGDATA --source-server=...`:
  - Несовместимые локальные сегменты WAL на `node1` откатываются назад.
  - На `node1` формируется файл `standby.signal`.
  - СУБД на `node1` стартует как `Slave` и начинает потоковую репликацию за `node2`.
- Кластер полностью восстанавливает согласованность без ручного вмешательства администратора!

---

## 4. Что делать при отклонении
1. Если `pg_rewind` завершается с ошибкой `target server needs to use either data checksums or "wal_log_hints = on"`:
   - Проверить наличие `wal_log_hints = on` в `postgresql.conf`.
2. Если `pg_rewind` падает с ошибкой аутентификации:
   - Проверить права пользователя `repl_user` на сервере: он должен обладать правами `REPLICATION` и правами на выполнение `pg_read_binary_file()`.
   - Проверить валидность пароля в `/var/lib/postgresql/.pgpass`.
