# Программа и методика испытаний (ПМИ) HA-кластера

Данный каталог содержит набор структурированных тест-кейсов для проверки отказоустойчивости, целостности данных и сценариев переключения двухузлового кластера высокой доступности, разворачиваемого скриптом [`bootstrap-ha.sh`](../bootstrap-ha.sh) и описанного диаграммами в каталоге [`mmd/`](../mmd/).

## 1. Архитектура тестового стенда

- **Узлы кластера**: `node1` и `node2` под управлением Linux.
- **Сетевые интерфейсы**:
  - **Ring 0 (Кольцо 0)**: прямой кабель/интерконнект между узлами (`10.0.0.1` <-> `10.0.0.2`), приоритет 100, порт 5405.
  - **Ring 1 (Кольцо 1)**: служебная сеть через маршрутизатор (`192.168.1.11` <-> `192.168.1.12`), приоритет 50, порт 5406.
- **Маршрутизатор**: `192.168.1.1` (Eltex / внешний шлюз, используемый как `ping-gateway`).
- **Виртуальный IP (VIP)**: `192.168.1.100/24` на интерфейсе `eth0`.
- **СУБД**: PostgreSQL 16 (порт 5432), multi-state ресурс Pacemaker `pgsql` (`ocf:heartbeat:pgsqlms`).
- **Балансировка и проверка роли**:
  - HAProxy слушает порт `127.0.0.1:5000`.
  - Порт проверки роли СУБД: `9200` (`db-role-check.socket` -> `/usr/local/bin/db-role-check.sh`).
- **Службы приложения**: разделены на критическое ядро `core-app-stack` (`haproxy-svc`, `my-app` в связке с `vip`) и второстепенный `daemon-svc` (`symmetrical=false`).
- **Служебные ресурсы и агенты Pacemaker**:
  - `fs-mon` (`ocf:heartbeat:Diskd`): защита раздела `/var/lib/pacemaker` от переполнения (порог 500 МБ).
  - `ping-gateway` (`ocf:pacemaker:ping`): мониторинг шлюза роутера с положительным правилом `pingd gt 0`.
  - `vip` (`ocf:heartbeat:IPaddr2`): с параметрами `run_arping=true arp_interval=500 arp_count=5`.
- **Служебные скрипты и юниты**:
  - `cluster-boot-analyzer.service` (`/usr/local/sbin/cluster-boot-analyzer.sh`) — проверка дисков, CIB, MTU, .pgpass, WAL.
  - `cluster-shutdown-marker.service` (`/usr/local/sbin/cluster-mark-shutdown.sh`) — фиксация роли при выключении.
  - `cluster-degraded-unblock.timer` / `.service` (`/usr/local/sbin/cluster-degraded-unblock.sh`) — 4-ступенчатый сторож деградации.

## 3. Общие правила проведения испытаний

1. Перед каждым тестом фиксируется статус кластера командой `pcs status`.
2. В процессе испытаний контролируются логи:
   - `journalctl -u pacemaker -u corosync -f`
   - `journalctl -t cluster-precheck -t cluster-watchdog -t cluster-state -f`
   - `tail -f /var/log/haproxy.log`
3. Время фиксации сбоя и переключения замеряется секундомером или таймштампами в системном журнале.
4. Ни один тест не считается успешным при возникновении состояния **Split-Brain** (одновременная запись на двух узлах или два активных VIP).
